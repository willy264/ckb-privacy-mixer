# How Privacy Mixer Withdrawal Works

## 1. What the User Brings to Withdrawal

The current withdrawal flow starts from an encrypted note, not from a browser vault or localStorage entry.

The user must provide:

- the encrypted note text shown during deposit or recovery
- the password used to encrypt that note

The frontend decrypts the note locally in memory. The password and plaintext note are not sent to the backend.

Plaintext note imports are rejected. This keeps the active flow aligned with the password-protected note model used by the deposit flow.

## 2. What Is Inside the Decrypted Note

After decryption, the note contains the data needed to prove ownership of one mixer deposit:

- `secret`: private random value generated by the browser before deposit submission.
- `nullifierSecret`: second private random value generated by the browser.
- `commitment`: public commitment derived from the two private secrets.
- `nullifier`: one-time spend marker derived from `nullifierSecret`.
- `sessionId`: deposit pool/session identifier.
- `sessionCommitments`: commitment snapshot for the anonymity set.
- `leafIndex`: the note's position in the commitment tree.
- `inputOutPoint`: finalized CT input outpoint.
- `stealthOutputAddress`: output address metadata from the deposit flow.
- `depositTxHash`: finalized deposit transaction hash.
- `runtimeMode: "live"`.

The backend may return finalized note metadata during recovery, but it cannot restore the private secrets. The frontend must merge that metadata with the original decrypted pending note and verify that the private secrets still derive the expected commitment.

If the note has `status: "pending"`, it cannot directly prepare a withdrawal proof. It must first be recovered or finalized.

## 3. Pending Note Recovery

If a user imports a pending recovery note, the frontend:

1. Decrypts the encrypted note in memory.
2. Calls the recovery endpoint with the note commitment.
3. Checks whether the coordinator knows that commitment.
4. Handles one of three outcomes:

- **Not found**: the deposit likely never reached backend registration, so the user can start a new deposit.
- **Pool not complete**: the frontend rebuilds a pending deposit tracker and sends the user back to the deposit panel to continue signing/finalization.
- **Finalized**: the frontend fetches finalized metadata, restores the original private secrets from the pending note, verifies the commitment, and shows a new encrypted finalized withdrawal note.

The finalized encrypted note is the long-term note used for withdrawal.

## 4. Preparing the Withdrawal Proof

When the user clicks **Prepare Proof**, the frontend:

1. Requires encrypted note text.
2. Requires the note password.
3. Decrypts the note locally in memory.
4. Rejects pending notes unless recovery/finalization succeeds first.
5. Rejects old preview/mock notes.
6. Verifies the note is a live 100 CT note.
7. Verifies `secret` and `nullifierSecret` derive the note commitment.
8. Refreshes the deposit session commitments from the backend when possible.
9. Builds the Merkle tree for the deposit session.
10. Locates the note's leaf index.
11. Generates the Groth16 withdrawal proof in the browser.
12. Builds the live CKB withdrawal transaction.

The proof says, in effect:

> I know the private secrets for one commitment in this session, and I am spending it only once.

It does not reveal which deposit belongs to the user.

## 5. Nullifier and Double-Spend Protection

The nullifier is derived from the private `nullifierSecret`.

During withdrawal, the transaction updates the live nullifier registry. This prevents the same note from being withdrawn twice. Once a nullifier has been accepted into the registry, another transaction using the same nullifier should be rejected.

## 6. Broadcast Direct

**Broadcast Direct** is the less private path.

The frontend:

1. Generates the ZK proof.
2. Builds the withdrawal transaction.
3. Asks the connected JoyID wallet to sign/pay for broadcast.
4. Broadcasts the transaction from the user's wallet context.

This can be useful for testing or emergency recovery, but it weakens privacy because the fee-paying wallet is visible on-chain.

If the same JoyID wallet that funded the original deposit also pays the withdrawal fee, observers may infer a connection between the deposit user and the withdrawal event.

## 7. Relay Private

**Relay Private** is the intended private path.

The frontend:

1. Generates the ZK proof locally.
2. Builds the withdrawal transaction locally.
3. Sends the prepared transaction and nullifier to the relayer.

The relayer:

1. Uses its own funded wallet to pay the CKB fee.
2. Broadcasts the prepared withdrawal transaction.
3. Returns the broadcast transaction hash.

The user's JoyID wallet is not used to pay the withdrawal fee in this path, so there is no direct on-chain fee-payment link between the user wallet and the withdrawal.

The relayer cannot generate a valid withdrawal without the user's proof, and it cannot change proof-bound transaction data without invalidating the transaction.

## 8. What Is Stored After Preparation

The frontend keeps prepared withdrawal state in memory for the current page session:

- prepared proof
- prepared transaction
- warning list
- session size
- registry size
- optional broadcast transaction hash

This state is not written to localStorage. If the page reloads, the user can paste the encrypted note again and prepare the proof again.

## 9. Failure Cases

Common failure cases now map to clear recovery paths:

- **Wrong password**: the encrypted note cannot be decrypted.
- **Plaintext note**: import is rejected; the user must use the encrypted note format.
- **Pending note**: recovery/finalization must happen before withdrawal proof generation.
- **Missing private secrets**: the note cannot produce a proof.
- **Commitment mismatch**: the private secrets do not belong to that deposit commitment.
- **Preview/mock note**: live withdrawal rejects it.
- **Unsupported denomination**: only 100 CT is currently supported.
- **Missing finalized metadata**: the note must be recovered/finalized first.

## 10. Security Boundary

The frontend handles private material:

- password
- decrypted note
- `secret`
- `nullifierSecret`
- ZK proof generation

The backend/relayer handles public or transaction material:

- deposit session lookup
- recovery lookup by commitment
- relayed transaction broadcast
- nullifier registry interaction

The backend should not receive the user's password, plaintext note, `secret`, or `nullifierSecret`.
