## Overview
This week focused heavily on debugging the end-to-end cryptographic and transaction construction flows for the deposit cycle. We successfully resolved several critical roadblocks spanning the backend Coordinator, the smart contract validation layer, and the Relayer polling mechanisms. We have now achieved a **fully functioning end-to-end deposit flow**, culminating in successful on-chain transaction broadcasts and local generation of the privacy notes.

## Key Accomplishments & Bug Fixes

### 1. JoyID Witness & Sighash Alignment
**Problem:** The transaction signature hash (sighash) generated by the frontend (via JoyID) did not match the sighash calculated by the backend coordinator, leading to signature verification failures.
**Solution:** Identified that JoyID automatically injects a 1000-byte placeholder lock for COTA sub-key witnesses. We updated the backend (`deposit-finalizer.ts`) to mirror this exact 1000-byte placeholder when building the unsigned transaction, perfectly aligning the sighash calculations.

### 2. Multi-Participant Witness Merging
**Problem:** When injecting the signed witnesses back into the final transaction, the backend would blindly overwrite the first witness, breaking multi-participant pools or cases where the same wallet signed multiple inputs.
**Solution:** Implemented a robust witness scan in `deposit-finalizer.ts` using `crypto.timingSafeEqual`. It now correctly searches for the matching placeholder lock and injects the returned signature exactly at the right index without disturbing other participants' signatures.

### 3. Smart Contract Verification Fixes (Errors 1 & 4)
**Problem:** The `ct-token-type` smart contract returned `IndexOutOfBound` (Error 1) and `Encoding` (Error 4) during the input/output sum check (`auth()`).
**Solution:** 
- The contract expected the mixed outputs to carry the `CT_TOKEN_TYPE` type script to balance the inputs and outputs. The backend was omitting this type script on the stealth outputs.
- We reconstructed the `CT_TOKEN_TYPE` script using the `CT_INFO_SCRIPT_HASH` and attached it to the mixed outputs.
- We also corrected the placement of the `ctTokenWitness` (the range proof) within the transaction's `witnesses` array. In CKB, `Source::GroupOutput` maps to absolute output indices; we adjusted the witness push order so the range proof aligns perfectly with the first mixed output at absolute index `N`.

### 4. Commitment Derivation Type Safety
**Problem:** `SyntaxError: Cannot convert 0x... to a BigInt` when generating the final Note Commitment. 
**Solution:** The coordinator was passing a raw UUID (`poolId`) containing hyphens into mathematical functions that expected a clean hex field element. We introduced a `sha256` hashing step to deterministically convert the UUID into a valid 32-byte session hex string before commitment derivation.

### 5. Relayer Polling Race Condition
**Problem:** The Relayer threw an unhandled `Deposit session not found` error immediately after a successful transaction broadcast, failing to display the note to the user.
**Solution:** The Coordinator's background cleanup job (`cleanupDepositPools`) was aggressively pruning `complete` pools from memory on its very next tick. We introduced a 10-minute grace period (`staleRound`) for completed pools, granting the Relayer ample time to poll the final transaction hash and output indices.
